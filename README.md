# deph

A CLI that audits the dependencies of every project in a repo — npm, Python, cargo, Go, Ruby, PHP — for known vulnerabilities, outdated versions, and licenses you don't allow, against a policy you commit to the repo in a `.deph` file.

```console
npx @deph/cli --help          # or npm install -g @deph/cli
pipx install deph-cli                        # or pip install deph-cli
```

The command is always `deph`. The package names differ per registry because `deph` was already taken on both: PyPI has it as `deph-cli`, and npm blocks that unscoped name as too similar to an existing `del-cli`, so npm is scoped.

Either route installs the same tool. deph is written in Python and has no dependencies at all — stdlib only — so the npm package just vendors the source and runs it with whatever `python3` is already on the box. Nothing to compile, nothing to `pip install`, no supply chain of its own. It needs Python 3.9+ present, which macOS and every Linux CI image already have; on Windows you may have to install it. Point `DEPH_PYTHON` at a specific interpreter if the one you want isn't first on `PATH`.

The npm route exists because a Node CI pipeline shouldn't need a Python setup step to audit its own `package-lock.json`.

It will also tell you, loudly, what it *couldn't* audit. A tool that reads one of six requirements and prints a green check is worse than one that crashes.

## Why I built it

I work across three products at once — a collaborative spreadsheet, an AI assistant platform, and a React Native app — in three separate repos, each with its own lockfile and its own CI pipeline. Answering "are we shipping anything with a known CVE?" meant `npm audit` three times and reading three walls of output, none of which agreed on what counted as a problem.

The part that actually wore me down wasn't finding vulnerabilities, it was the second run. `npm audit` has no memory: something the team looked at and consciously accepted is reported identically the next day, so the output stops being read. It has nothing to say about licenses. And there's no way to say "this is our bar" once and apply it to all three repos, so each pipeline ends up with its own hand-rolled `grep` and threshold.

What I wanted was one file, committed to the repo, that states what we consider unacceptable — including the things we've accepted and why — and one command in CI that answers yes or no against it. A waiver then becomes a line in a PR that someone reviews, with a reason attached and a date it expires, rather than a flag buried in a pipeline script.

So the design is taken fairly directly from Prisma: an installed CLI plus one declarative file that the tool both reads and writes into. You own the top of the file, `deph scan` owns the bottom.

The scanners cover more than npm because the discovery and registry layers are a plugin registry, and once that exists an ecosystem is a class and one `register()` call. I use the npm ones; the rest are tested against fixtures and a corpus of real open-source repos rather than daily use.

```text
policy {
  fail vuln     >= high for direct
  warn vuln     >= high for transitive
  warn vuln     >= low
  fail license  not [MIT, Apache-2.0, BSD-2-Clause, ISC, 0BSD, BlueOak-1.0.0] for prod
  warn lag      >= major for prod
  warn unresolved >= 1
}

waive GHSA-xxxx-yyyy-zzzz until 2026-09-01 "vendored code not exposed; upgrade planned Q3"

// ---- generated by deph scan @ 2026-07-27 10:00 UTC — do not edit below ----

project "web/frontend" ecosystem=npm manifest="package-lock.json" {
  dep axios 0.21.1 -> 1.18.1 license=MIT fix=0.21.2 [vuln:high:GHSA-hfxv-24rg-xrqf, lag:major]
  dep follow-redirects 1.14.0 -> 1.16.0 license=MIT transitive [vuln:medium:GHSA-r4q5-vmmm-2653]
  dep jest 27.5.1 -> 29.7.0 license=MIT dev [lag:major]
  unresolved "sibling@workspace:*" reason=workspace name=sibling
}
```

Everything above the marker survives a re-scan byte for byte. Everything below is regenerated. Two scans with no dependency changes produce no diff except the timestamp, so the file is reviewable — a PR that introduces a vulnerability shows up as a line with a GHSA id in it.

`.deph` is its own format with its own grammar, not YAML or TOML with a funny extension. There's a real tokenizer and recursive-descent parser behind it and errors come back as `repo.deph:4:3`. The grammar is written out as EBNF in [docs/SPEC.md](docs/SPEC.md).

## Running it

```console
cd your-repo
deph init      # writes repo.deph with a starting policy
deph scan      # finds manifests, looks up versions and advisories, fills in the file
deph check     # applies the policy; exit 1 if anything fails
deph studio    # dashboard on localhost: grades, advisory links, filters
```

| Command | Does |
|---|---|
| `deph init` | Writes `repo.deph`. Won't overwrite an existing one. |
| `deph scan` | Walks the tree for every manifest it knows, looks up versions, licenses and advisories, rewrites the generated section. `--offline` uses only the cache; `--advisories github` swaps OSV for the GitHub Advisory Database. |
| `deph check` | Applies the policy to what's in the file. No network, so it's reproducible and fast. Exit 1 on any failing finding. Emits `::error::`/`::warning::` under GitHub Actions. `--format json` for scripts, `--format sarif` for GitHub code scanning. |
| `deph sbom` | A CycloneDX 1.5 SBOM of the scanned dependencies, with the vulnerabilities attached and waived ones marked `not_affected`. |
| `deph studio` | Serves the dashboard on `127.0.0.1:5397` and opens a browser. Rebuilt from the file per request, so edit and refresh. |
| `deph render -o report.html` | Same dashboard as one self-contained HTML file, for uploading as a CI artifact. |
| `deph validate` | Parses and lints: malformed rules, unknown severities, duplicate projects, waivers without reasons, expired waivers, scopes that can never match. |

Commands find the single `.deph` file in the tree themselves. If there are several they stop and ask you to pass `--file`, because picking one by guesswork would mean auditing against the wrong policy.

## What it reads

| Ecosystem | Manifests, best first |
|---|---|
| npm | `package-lock.json` (v1/v2/v3), `pnpm-lock.yaml`, `yarn.lock` (classic and berry), `package.json` |
| Python | `poetry.lock`, `uv.lock`, `Pipfile.lock`, `requirements*.txt`, `pyproject.toml` |
| cargo | `Cargo.lock` + `Cargo.toml` |
| Go | `go.sum`, `go.mod` |
| Ruby | `Gemfile.lock` |
| PHP | `composer.lock` |

One project per language per directory: a repo with both `package-lock.json` and `yarn.lock` has one set of node dependencies, and scanning both would double-report every finding. Several `requirements*.txt` files in one directory are treated as several real dependency sets, except when one includes another with `-r`.

In a pnpm or yarn workspace the root lockfile already pins every member's dependencies, so member `package.json` files are skipped rather than having all their ranges reported as unresolved. A member that commits its own lockfile is still scanned as its own project. (On a real monorepo, not doing this produced 165 phantom "unresolved" entries.)

## Trying it on a repo you don't want to modify

`deph scan` normally writes the `.deph` file next to the code it describes. To audit a checkout without leaving anything in it, keep the file elsewhere and point `--root` at the tree:

```console
mkdir ~/audits && cd ~/audits
deph init --file myrepo.deph
deph scan --file myrepo.deph --root ~/code/myrepo
deph check  --file myrepo.deph
deph render --file myrepo.deph -o myrepo.html
```

Nothing is written inside `~/code/myrepo`. Useful for a first look, for auditing code you don't own, and for scanning several repos into one directory of reports.

The lower a manifest is in that list, the less it can tell you. A `package.json` or a `pyproject.toml` declares *ranges*, so most of what it names ends up in the unresolved column rather than being audited — see below.

## Partial scans are visible

Every requirement deph can't pin to a single version is recorded with a reason, counted, and reported:

```console
$ deph check
  WARN   unresolved  services/api  6 dependencies in services/api/requirements.txt
                                   could not be pinned to a version and were not
                                   audited (1 local, 1 missing, 2 range, 2 unpinned)
deph check: FAIL (3 fail, 7 warn, 0 waived)
  audited 69 dependencies across 12 projects; 24 could not be pinned and were skipped
```

The default policy has `warn unresolved >= 1` for this reason. Raise it to `fail unresolved >= 1` if you want unpinnable dependencies to break the build, which is a reasonable thing to want.

`deph check --format json` reports the same thing as a `coverage` object, and the dashboard shows a per-project "% audited" next to the grade. A project can't get an A by being unreadable.

## Policy details worth knowing

A high vulnerability matches both `fail vuln >= high` and `warn vuln >= low`. It's judged once, at the stronger level — you get one fail, not a fail and a warn.

Rules can be narrowed with `for direct`, `for transitive`, `for dev` or `for prod`. Most teams want to fail on their own dependencies and merely know about the tail behind them, and a build-only test runner is not the same risk as something you ship.

Licenses go through a real SPDX expression evaluator, so `(MIT OR GPL-3.0-only) AND Apache-2.0` is answered correctly rather than by string matching. `WITH` exceptions, `+`/`-or-later` suffixes, deprecated ids like `GPL-2.0`, and npm's `MIT/Apache-2.0` spelling all work. An expression deph can't parse is *not* allowed: something we can't read is something we can't certify.

Version comparison is per-ecosystem, because PEP 440 and semver genuinely disagree. `1.0.post1` is newer than `1.0` in Python and older in npm; both readings are right for their own ecosystem, so a shared comparator has to be wrong for one of them. Getting this wrong means missed advisories or invented ones.

Advisories come from [OSV.dev](https://osv.dev) by default, which aggregates GHSA, PyPA, RustSec, Go and others, and does version-range matching server-side. Scanning the test fixtures both ways, OSV returned 199 distinct advisories against GitHub's 163 — but five of GitHub's weren't in OSV's answer, so neither source strictly contains the other. If you need the broadest possible coverage, run both and merge; `--advisories github` switches sources.

Findings carry the version that fixes them, so the output is actionable and not just a list of problems.

GitHub's REST API reports `medium` where its own web UI says `moderate`, so both are treated as `medium`. A severity deph doesn't recognise ranks below `low` and matches nothing, rather than crashing or being treated as critical.

`waive <id> "<reason>"` turns a finding into a `waived` one: still listed, struck through in the dashboard with the reason, never failing, and it survives every re-scan. Use an advisory id for vulnerabilities, `license:<dep>` or `lag:<dep>` for the others. The reason is required, which is the entire point — a waiver with no explanation is just a disabled check.

Waivers can expire: `waive GHSA-x until 2026-09-01 "waiting on upstream"`. After that date the finding comes back at full severity, flagged as an expired waiver rather than a new problem. A permanent waiver is a permanent blind spot.

## In CI

```yaml
- uses: actions/setup-python@v5
  with: { python-version: "3.12" }
- run: pip install deph-cli
- run: deph scan
  env: { GITHUB_TOKEN: ${{ secrets.GITHUB_TOKEN }} }   # advisory rate limits
- run: deph check
- run: deph render -o deph-report.html
- uses: actions/upload-artifact@v4
  with: { name: deph-report, path: deph-report.html }
```

In a Node pipeline, skip the Python setup step — the runners already have an interpreter:

```yaml
- run: npx @deph/cli scan
  env: { GITHUB_TOKEN: ${{ secrets.GITHUB_TOKEN }} }
- run: npx @deph/cli check
```

`deph check` needs no network, so it also works as a fast required check against the committed file with no scan step at all.

For code scanning, feed it SARIF instead:

```yaml
- run: deph check --format sarif > deph.sarif
  continue-on-error: true          # upload the results even when the gate fails
- uses: github/codeql-action/upload-sarif@v3
  with: { sarif_file: deph.sarif }
```

There's also a pre-commit hook, which runs `deph check` when a `.deph` file or any lockfile changes:

```yaml
repos:
  - repo: https://github.com/sayyedfaisal06/deph-cli
    rev: v0.1.0
    hooks:
      - id: deph-check
```

### Private registries

deph reads the variables the native tools already use, so a configured CI box usually needs nothing new: `NPM_CONFIG_REGISTRY`, `PIP_INDEX_URL`, `GOPROXY`. Each has a `DEPH_`-prefixed override (`DEPH_NPM_REGISTRY`, `DEPH_PIP_INDEX_URL`, `DEPH_CARGO_REGISTRY`, `DEPH_GO_PROXY`, `DEPH_GEM_SOURCE`, `DEPH_COMPOSER_REPO`) that wins, plus a matching `DEPH_*_TOKEN` sent as a bearer token.

Set `GITHUB_TOKEN` even when using OSV. Unauthenticated GitHub allows 60 requests an hour, and on a shared CI IP that runs out fast; when it does, the circuit breaker trips and you get partial data with a warning rather than a hang.

### Exit codes

| Code | Meaning |
|---|---|
| 0 | No failing findings. Warnings may still have been printed. |
| 1 | At least one `fail` finding, or `validate` found an error. |
| 2 | Couldn't get far enough to judge: no `.deph` file, several of them, or a parse error. |
| 130 | Interrupted. |

Exit 2 is deliberately distinct from exit 1. A missing file is not a clean audit, and CI shouldn't treat it as one.

### `deph check --format json`

Schema 2. Fields may be added; existing ones keep their meaning.

```json
{
  "schema": 2,
  "file": "repo.deph",
  "ok": false,
  "summary": { "fail": 2, "warn": 3, "waived": 1 },
  "coverage": {
    "audited": 69,
    "unresolved": 24,
    "unresolved_by_reason": { "range": 14, "local": 6, "vcs": 3, "missing": 1 },
    "projects": 12
  },
  "findings": [
    {
      "project": "web/frontend",
      "dep": "axios",
      "version": "0.21.1",
      "kind": "vuln",
      "level": "fail",
      "id": "GHSA-hfxv-24rg-xrqf",
      "detail": "high",
      "message": "axios 0.21.1 has a high severity vulnerability (GHSA-hfxv-24rg-xrqf); fixed in 0.21.2",
      "transitive": false,
      "dev": false,
      "fix": "0.21.2",
      "url": "https://github.com/advisories/GHSA-hfxv-24rg-xrqf",
      "cvss": null,
      "cwe": "CWE-918",
      "waived_reason": null,
      "waiver_expired": false
    }
  ]
}
```

`kind` is `vuln`, `lag`, `license` or `unresolved`; `level` is `fail`, `warn` or `waived`.

`coverage` is the reason this is schema 2 rather than 1. Without it, a consumer can't tell a clean scan from one that only managed to read a third of the manifests.

## Caching

Latest versions and licenses come from registry.npmjs.org, the pypi.org JSON API, crates.io, proxy.golang.org, rubygems.org and packagist.org; vulnerabilities from OSV.dev or the GitHub Advisory Database. Every response goes into a sqlite file in your user cache directory (`DEPH_CACHE_DIR` overrides), so re-scans are cheap and `--offline` works on a plane.

When a registry is unreachable, deph serves the newest thing it has cached even if that's past the TTL, warns, and carries on. So results from a degraded or offline run are a floor, not a current answer; the next online scan refreshes them.

## Known limitations

- **No Maven, Gradle, NuGet or Conan.** Adding one is a scanner class and a `register()` call — the registry is built for it and [CONTRIBUTING.md](CONTRIBUTING.md) walks through it — but I haven't written them.
- **Unpinned dependencies are reported, not resolved.** `flask>=2.0` lands in the unresolved column with a reason. deph doesn't run a resolver, so it can't tell you which version you'd actually get. If you want those audited, commit a lockfile.
- **Every pin in a `requirements.txt` is reported as direct**, because a requirements file is a list of things someone asked for. Point deph at a `pip freeze` dump and it'll call the whole transitive tree direct.
- **`uv.lock` has no dev/direct information**, and Gemfile groups aren't in `Gemfile.lock`, so those flags stay false rather than being guessed at. `deph check --format json` will under-report `dev` for those ecosystems.
- **Go licenses are missing.** The module proxy doesn't serve them and pkg.go.dev has no API, so Go dependencies get versions and advisories but no license data.
- **Grades are a judgement call, not a standard.** The score starts at 100 and subtracts per finding (30 for a critical, 5 for a major version behind). It's there to sort projects worst-first in the dashboard; don't put it in a report to your board.
- **A `[patch]`ed or git-sourced crate is reported as unresolved**, not audited. The built code isn't the registry release, so advisories about that version would be about different code.
- **`go.sum` legitimately lists several versions of one module.** Filtering to the one that actually builds needs Go's minimal version selection, which deph doesn't implement, so you may see two rows for one module.

The full set of shapes each scanner declines to handle is in the module docstrings, and `tests/corpus/run_corpus.py` scans real repositories to keep that list honest — most of the entries above were found by running it rather than by thinking hard.

### What I'd do differently

The generated section stores findings per dependency, which means a vulnerability affecting six packages is written out six times. Storing advisories once and referencing them would make the file smaller and the diffs better, but it'd hurt the thing I care about most: right now you can read a single `dep` line and know everything about that dependency.

I'd also have written the cache with an explicit schema version from the start. It's keyed by URL and the values are raw API responses, so the day an upstream API changes a field I get to invalidate everything by hand.

And I'd have built the unresolved channel first. I wrote the pip scanner to skip anything it couldn't pin, which was fine until someone pointed out that a realistic `requirements.txt` audited as one dependency out of six and still printed a green check. Everything about coverage reporting in here is a retrofit of something that should have been the first design constraint.
